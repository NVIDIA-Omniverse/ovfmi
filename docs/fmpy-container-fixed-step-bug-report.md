# GitHub issue report for FMPy

## Resolution

Fixed upstream by [FMPy PR #889](https://github.com/CATIA-Systems/FMPy/pull/889)
and released in FMPy 0.3.32. ovfmi verified the stock runtime with the original
60-step reproduction and a 600-step native conveyor run, then retired its local
Container FMU runtime patch.

## Suggested title

Container FMU rejects valid 60 Hz steps generated by `simulate_fmu()` because
of floating-point rounding

## Issue body

### Description

An FMI 2 container created by FMPy with
`fixedInternalStepSize=1 / 60` cannot be simulated for one second by FMPy's own
`simulate_fmu()` using the same nominal step and output interval.

The sixth `fmi2DoStep()` receives a communication step of
`0.016666666666666677`. This is the difference between adjacent communication
points calculated by `simulate_fmu()`. The container divides this value by its
fixed step, obtains `1.0000000000000007`, and rejects it as not being an even
multiple of the fixed step.

This occurs with an ordinary one-component container constructed through the
public `fmpy.container_fmu` API. SSP and ovfmi are not involved.

### Environment

- FMPy 0.3.30 from PyPI
- Windows 11, x86_64
- Python 3.12

The relevant comparison remains present on FMPy `main` at commit
`b8eee934b71941a33a66540bebd5defe22327e89` (version 0.3.31).

### Reproducer

Run this script from the root of a clone of the FMPy repository. It uses the
repository's existing `tests/resources/Controller.fmu` fixture.

```python
from pathlib import Path
from tempfile import TemporaryDirectory

from fmpy import read_model_description, simulate_fmu
from fmpy.container_fmu.cli import create_container_fmu
from fmpy.container_fmu.config import Component, Configuration
from fmpy.model_description import (
    CoSimulation,
    DefaultExperiment,
    ModelDescription,
    ModelVariable,
)


fixed_step = 1.0 / 60.0
component_fmu = Path("tests/resources/Controller.fmu").resolve()
component_md = read_model_description(component_fmu)

component = Component(
    name="controller",
    filename=component_fmu,
    modelDescription=component_md,
)

component_y = next(
    variable
    for variable in component_md.modelVariables
    if variable.name == "y"
)

container_y = ModelVariable(
    name="y",
    type="Real",
    causality="output",
    variability="continuous",
    initial="calculated",
)

container_md = ModelDescription(
    fmiVersion="2.0",
    modelName="MinimalContainer",
    instantiationToken="",
    defaultExperiment=DefaultExperiment(
        stopTime="1",
        stepSize=str(fixed_step),
    ),
    coSimulation=CoSimulation(
        fixedInternalStepSize=fixed_step,
    ),
    modelVariables=[container_y],
)

configuration = Configuration(
    parallelDoStep=False,
    modelDescription=container_md,
    components=[component],
    connections=[],
    variableMappings={
        container_y: [(component, component_y)],
    },
)

with TemporaryDirectory() as temporary_directory:
    work = Path(temporary_directory)
    build_directory = work / "build"
    build_directory.mkdir()
    container_fmu = work / "Container.fmu"

    create_container_fmu(
        configuration,
        build_directory,
        container_fmu,
    )

    result = simulate_fmu(
        container_fmu,
        stop_time=1.0,
        step_size=fixed_step,
        output_interval=fixed_step,
        output=[],
    )

    print(result["time"][-1])
```

### Actual result

```text
fmpy.fmi1.FMICallException: fmi2DoStep failed with status 3 (error)
```

The failure can be reduced to these values at the sixth call:

```text
currentCommunicationPoint = 0.08333333333333333
communicationStepSize     = 0.016666666666666677
fixedStepSize             = 0.016666666666666666
step ratio                = 1.0000000000000007
```

### Expected result

The container accepts the representational rounding in the communication step
and completes the one-second simulation.

### Root cause

`simulateCS()` calculates regular communication points by multiplication and
then derives the step by subtraction:

```python
next_regular_point = start_time + (n_steps + 1) * output_interval
step_size = next_communication_point - time
```

This is a sensible way to avoid cumulative drift, but the resulting difference
is not guaranteed to be bit-identical to `output_interval`.

The native container runtime calculates the number of internal steps and uses
`approx::relative_eq!` with its default tolerance:

```rust
let n_steps_float = communicationStepSize / self.system.fixedStepSize;
let n_steps = n_steps_float.round() as u64;

if n_steps == 0 || !relative_eq!(n_steps as f64, n_steps_float) {
    // log error and return fmiError
}
```

The default tolerance is too strict for the rounding produced by FMPy's own
simulation loop at common rates such as 60 Hz.

The container has a similar default-tolerance comparison between
`currentCommunicationPoint` and its reconstructed internal time:

```rust
if relative_ne!(currentCommunicationPoint, self.time()) {
    // log error and return fmiError
}
```

That comparison can likewise reject a master that advances time through
repeated floating-point addition.

### Suggested correction

Use an explicit tolerance appropriate for communication-time calculations in
both checks. For example, compare the absolute difference against a small
relative tolerance scaled to at least `1.0`, rather than using the default
machine-epsilon-level tolerance:

```rust
fn time_close(a: f64, b: f64) -> bool {
    let scale = a.abs().max(b.abs()).max(1.0);
    (a - b).abs() <= 1.0e-12 * scale
}
```

The exact tolerance is a project decision, but it must accept normal rounding
from subtraction of adjacent communication points.

As a regression test, generate a container with `fixedInternalStepSize=1 / 60`
and simulate at least one second using `simulate_fmu()` with
`output_interval=1 / 60`.

### Confirmed diagnostic workaround

Calling the same container 60 times with

```python
currentCommunicationPoint = n * fixed_step
communicationStepSize = fixed_step
```

completes successfully. This confirms that the failure is caused by rejecting
the subtraction-derived representation of the step, rather than by the nested
FMU.
